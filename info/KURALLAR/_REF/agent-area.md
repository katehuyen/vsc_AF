# AGENT_AREA Terminal — Operating Procedures

`00_AGENT_AREA` is the agent operating terminal (input/output + system definition + logs). Its human-side definition lives in vault `99_SYSTEM/` (`A-REF - Sistem Haritası` + `A-REF - AGENT_AREA Klasör Sözlüğü`).

**A. Filing (`00_INPUT/01_YERLEŞTİR`) — the single entry gate.** Procedure: read → **look for an existing home** → think holistically → `K-CAT - Name.md` with provenance frontmatter → move via Obsidian MCP/Local REST API (`_REF/vault-write.md`). **Judgment belongs to opus (manager):** whether it is the right home or needs a new folder — including cases that look like a home but should not be one — requires nuance, coherence, and consistency; wrong filing costs a lot of time and breaks system consistency → **manager does the reasoning**, the move itself is easy. If another agent is told to file something, it helps but **leaves ambiguous or critical judgment to manager**. After every filing, a row is added to the TOP of **`01_YERLEŞTİR/_LOG_.md`**: **date-time `YYYY-MM-DD HH:MM`** · original · target→new name · agent · 🤖 AI note. **The time is mandatory on EVERY row.** `_LOG_.md` is never deleted or moved.

**B. Two-way `_LOG_` scanning.** The folder is scanned **both for new files and for new 🧑 user comments**. If a row has 🧑 filled and ✔ empty: do what it asks, then **stamp** the ✔ column — `-DONE-` / `-YAPILAMADI- (reason)` / `-SORU- (question)` / `-NOT- (extra info)`. A stamped row has been handled and is not processed again. This log is an **optimization tool**: learn from the user's corrections and make fewer mistakes over time.

**C. Archive mirroring (INPUT & OUTPUT).** Every active folder has a one-to-one `_ARCHIVE` counterpart under `99_ARCHIVE` (`01_YERLEŞTİR`→`01_YERLEŞTİR_ARCHIVE`, `10_REPORT`→`10_REPORT_ARCHIVE`…). A finished file is deleted if worthless, or **transferred to its counterpart** if worth keeping. If an active folder is added, renamed, or removed, its counterpart changes in parallel — this goes without saying.

**D. Reports & Knowledge Base (OUTPUT).** Reports → `00_OUTPUT/10_REPORT` (`YYYY-MM-DD_<agent>_<name>.md`, `_REF/notices.md`). The permanent **knowledge base** → `00_OUTPUT/20_KNOWLEDGE_BASE`, format `KB<YYMMDD><NN> - <Main Topic> - <Sub Topic> - <Name>.md` plus **plenty of `tags`** in frontmatter. A highly informative report can be transferred into the KB; or, when the user says "research this and write it into the KB", it goes straight there.

**E. `02_MEDIALAŞTIR` — the media twin of filing.** Input at `00_INPUT/02_MEDIALAŞTIR/media_<base>/<stage>/`; the agent scans → moves under `D:\zome\media\media_<base>\<type>\<stage>\` → deletes the source → records it in the engine with `airtable_media_save`. Base-agnostic (the base name is read from the folder, never hardcoded); type comes from the extension; stage `source/raw/semi/final/asset` → `workflow.stage` (source = input material · raw = unclassified but kept, nothing is thrown away · semi = half done · final = truly succeeded · asset = reusable treasure; `media_<base>\all_in\` = the waiting area for unprocessed files the user drops — agents never put their output there; it is processed only by `media.allin`, X-422: a model stages each file, a sure one is filed + recorded + its form filled, the rest stay and are asked). The record is filled field by field like the Admin panel's entry form — the form does most of the classifying, the folder is the last link; failures are kept with their failure fields. If the engine is down: `af.js airtable.start instance=<base>` (hidden, no browser; `start_admin.bat` is the person's door). **A workflow run files and records its own output** (Agent Farm X-418: every media/tool step file → its stage folder + a full record, FAIL/left-out → raw, the run's last output → final, its outside inputs → source; records wait in `media.pending` while the engine is down) — never re-file a run's product by hand. What a run's end did in the library (promotions, each record's enrichment or why it failed) → `workflows.status` → `libraryEnd`; redo a failed one with `media.enrich`. The whole chain (X-423): run → filed + recorded → form at the end → Studio wall → promote to asset → the next run's `airtable` input (`stages: asset`) takes it, its products name the asset as their cause. One file outside a run: `media.record` (file + record + fingerprint dedupe in one call); a stage change or a promotion to asset: `media.restage` (moves the file AND updates the record). A record's meaning sections (identity, taxonomy, function, tone, education, marketing, platform, accessibility, seo, tags, salvage notes) are filled by a model that looks at the file — at a run's end for its final and failed files (X-419, `library.enrich.*`), or one record with `media.enrich`; only blank fields are filled, so fill by hand only what a model cannot see. A workflow takes its material FROM the library with an input of type `airtable` (a search run before step 1, its records the value; X-420, `airtable.input.*`); preview the same search with `media.find`. Log: `02_MEDIALAŞTIR/_LOG_.md` (same date-time rule).
