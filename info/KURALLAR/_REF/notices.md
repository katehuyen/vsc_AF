# Notices — the Agent↔User Message Board

**The single shared channel agents use to tell the user something or ask them something: the Notices board on the Agent Farm dashboard** (status-bar bell + "🔔 Notices" on every page). The user sees **titles** on the root page and opens one to read it. Written and read through bridge ops (`_REF/bridge.md`).

**Golden rule — one thing = one notice.** Every piece of news / result / reminder / question you want to deliver becomes **a single row**. Do not turn each sub-part of a job into its own notice — it floods the root page and means nothing. Deliver multi-part content as `sections` inside one notice.

**Two axes plus a user marker:**
- **type** (7 options — pick the one that matches the nature of the work): `update` (news / general development), `report` (report / delivery), `result` (outcome of a job / completed), `reminder`, `suggestion` (idea / proposal), `warning`, `question` (a question for the user).
- **level** (importance — **MANDATORY**, every notice has one): `1` routine/daily · `2` medium · `3` important · `4` ultra (very rare, critical). Row color and notification depend on it. **Never leave a notice without a level** — pick honestly from 1-4, do not inflate (not everything is a 3 or 4).
- **stars** (0-3): the **user's** own marker; agents never set it. (The user may also edit, search, and export notices — that is their side; you just post correctly.)

**Content — a link is not enough, summarize.** After reading `body`/`sections` the user should understand the topic **without having to follow the link**. Give the link, but also summarize what is behind it. Structure: `title` = the root row (one clear sentence) · `body` = markdown, the whole short message · `sections: [{title, body}]` = multi-heading content (each section expands separately for the user and **is fully self-contained**).

**THE SECOND LEG — short notice + a full report that opens on click (‼️ the adopted pattern).** The notice board is for **short** messages written into a single JSON; that format inevitably pushes the writer to compress. But not every piece of work is short. **Rule: when the volume of information is meaningful, a notice works on two legs** — (1) the **summary** on the board (title + body/sections), and (2) a **substantial MD report file** linked to it. Do not settle for something tiny: leave the summary on the board, put the **depth in the report**.
- **How:** pass `report:"<full markdown>"` to `notices.post` → the system writes it into the **default report folder** and links it on the notice as "📄 Open full report". The host adds the `YYYY-MM-DD_<agent>_` prefix automatically; if you pass `reportName?`, give **only the short topic name** — **do not include the date or agent** (otherwise you get a doubled prefix). `reportPath?` links a file you already wrote yourself. The user reads the summary on the board and the full text in the file.
- **Default report folder:** `D:\zone\know\note\obsidian\00_AGENT_AREA\00_OUTPUT\10_REPORT` — the **single shared place** agents report into; no agent writes reports into its own folder (configurable via the `agentFarm.reportDir` setting). **Naming: `YYYY-MM-DD_<agent>_<short-name>.md`** — date, then agent name, then topic. Because all reports share one folder, the agent name in the filename is **mandatory**.
- **Report content:** Turkish, in your own voice, **substantial** — not inflated headings, but real depth for whoever wants it. **Always append source URLs at the end.**
- **When:** "give me a report / brief me on X / send me this daily or weekly", daily/weekly AI digests, the outcome or output of a piece of work, a summary of anything — all of these use this pattern. A plain short piece of news, a reminder, or a question needs no second leg; the short message is enough.
- **RULE — a report means a linked announcement on Notices (no exceptions, ALL agents):** every agent that produces an MD report in `10_REPORT` **must** announce it on Notices with a short **linked** message (`report:` links it automatically when writing new; use `reportPath:` for a file you already wrote). **A report file with no announcement on the board = the job is half done** — the user must never have to track reports outside the board; the board is the single entry point.

**‼️ POST ONCE — `notices.post` IS A WRITE, NEVER AN INSPECTION.** Measured 2026-09-13: an agent piped its own post answer through `head -8`, could not see the id it had been handed, and ran the identical command again to read the fields — the user got the same question on the board twice. Three rules follow: **read the answer of the call you made** (never truncate a write op's answer — `--out` it or widen the filter, but do not re-run it); **to change what a notice says use `notices.edit`**, never a second post; **to take one off the board use `notices.dismiss`** (undoable with `notices.undo`) — `notices.resolve` only marks a question handled and leaves the row exactly where the user sees it, so it is not a retraction and checking your own pending list will not show the copy. Agent Farm now refuses an identical agent+title+body within 10 minutes (`posted:false`, `duplicateOf`) and hands the first notice back; `allowDuplicate:true` is for saying something twice on purpose.

**How to write:** bridge op `notices.post` (args: `title`, `type?`, `level?`, `body?`, `sections?`, `tags?`, `agent?`, `dueAt?`, **`project?`**, **`report?`/`reportName?`/`reportPath?`**; recipe in `_REF/bridge.md`). Pass `agent` as your own name. No spam — only what is genuinely worth delivering.

**‼️ WHICH PROJECT IT IS ABOUT — you say it, or Agent Farm says it for you.** A notice that lands as "No Project" leaves the user filing your work by hand. So:
- **In a project session** (your prompt opened with `=== AGENT FARM PROJECT CONTEXT ===`) — say nothing. Agent Farm stamps the session's own project for you and the answer comes back with `projectFrom`; **check that field**, because it only fills in when the answer is unambiguous.
- **Working on a project WITHOUT a project session, or telling the user about a different one** — pass `project:"<id or name>"` yourself. A name nothing matches is reported back (`projectError`) and the notice posts unfiled; it is never guessed at.
- **Genuinely about no project** (a fleet-wide observation, a question about the agent system) — pass `project:"(none)"` to say so out loud, rather than leaving it to be inferred.

**Leaving a question (`question` type) — asynchronous Q&A:**
- Questions that need clarifying so you can work better later, but do not have to be asked in chat right now (a project detail, a user preference, something you want to write to memory, self-optimization) are left with `type:"question"`. The user answers **from the UI** when they get the chance (→answered) or **closes it without answering** (→declined = they did not take it up; notice this and draw your own conclusion).
- **Every turn, before starting work**, track your own notices on **both** boards — answering a question (or converting any notice) **deletes it from Notices by default** and the answer lives only in the queue, so Notices alone can never tell you "unanswered":
  - (a) `notices.list { agent:"<you>", type:"question", handled:false }` — still open, or answered with the notice kept. If answered, **act on it** (save to memory / apply), then `notices.resolve`; if declined, take note and resolve it.
  - (b) `queue.list { sourceNoticeAgent:"<you>", active:true }` — any notice of yours (question or not) the user answered or turned into work. The item carries the whole notice (`sourceNoticeTitle/Type/Body/Sections/ReportPath`, its project) and is targeted at you: **you own it directly** — manager does not delegate it — so act, then close it with `queue.stamp`.
  - In neither list = resolved or deleted; never re-ask it. (Wired as an `[every-turn]` duty in `DUTIES.md`.)
- Never ask the same question twice; anything needing fast action is asked directly in chat. Reading, pinning, starring, and deleting belong to the user; the agent only posts and resolves its own questions.

**‼️ ASKING IN CHAT (`AskUserQuestion`) — READ THE RESULT BEFORE YOU BELIEVE IT.** MEASURED over the whole transcript history: when the answer carries free text, the CLI hands you **only** `"The user responded: <text>"` and silently **drops every option the user ticked** — one real call threw away all four of their choices. So a result starting `The user responded:` means **you may be holding half an answer**, not that they ignored the options. The picks are not lost, only hidden: your own transcript (`_run_folder_move\claude\projects\<project>\<sessionId>.jsonl`, the record whose `toolUseResult` has `questions`) keeps them in `toolUseResult.answers`. Read that before re-asking — re-asking what they already answered is what annoys them most. If you cannot recover them and the choices change what you do, ask again in one short line; never pick for them (Principle 2).

**Posting is not delivering — the board now ages.** An unread level-3+ notice, or an unanswered `question`, older than `agentFarm.noticeStaleHours` (default 24h) turns the status-bar bell into a warning naming the oldest item, raises a row on the **Living** page, and nags **once** per unanswered question. Consequences of this for you: pick `level` honestly (inflating it will now actively pester the user), and **never post a level-3 notice for something that does not need reading**. If a question of yours has aged, do not re-ask it — it is already insisting on your behalf.
