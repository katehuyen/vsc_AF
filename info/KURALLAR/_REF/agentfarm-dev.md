# Agent Farm Development — Bridge Compatibility Is MANDATORY

Binding on **whichever agent** works in `D:\zone\dev\git\miropharm\vsc_AgentFarm`. The goal is not that today's feature reaches the bridge, but that **every future feature** does too.

1. **Rule:** Every new function the user can trigger from the command palette or a panel, and that an agent could reasonably trigger by instruction (a new panel button, a new command, a new task type, a new mission/workflow capability…), is added **in the same commit** as a `register(...)` entry in the `BridgeRegistry` in `src/core/bridge.ts`. This is not a separate "I'll do it later" task — it is **part of the feature's definition of done.**
2. **How:** Add a new `{ op, describe, handler }` to the `bridge.register([...])` block in `src/extension.ts`. The `op` name follows `<area>.<verb>` (`tasks.add`, `missions.start`); `describe` states in one line what it does and its `args` — agents calling `farm.ops` will read this, so it must be clear. The `handler` **calls** the existing manager/service method; it never reimplements the logic (the single source of truth is the code the UI uses).
3. **Exception:** Purely visual/navigational features (a page's color theme, a chart's layout) do not go on the bridge — only functions that **read data or trigger an action** do. **Secrets** is a deliberate security exception (`_REF/bridge.md`).
4. **Verification:** Add a dispatch test for the new op following the `test/test_bridge.js` pattern; confirm the new entry appears in the `{ "op": "farm.ops" }` output.
5. **‼️ THE RULE IS NOW MEASURED, so it fails the build rather than your memory.** `test/test_parity.js` reads every contributed command, right-click item and panel message handler and checks each against `parity.manifest.json`. A new user-triggerable action MUST get an entry there in the same commit — with its op(s), or one of five exemptions (`navigation` · `visual` · `file-picker` · `secrets` · `human-only`), or a named `gap` saying what the missing op would do. "Later" is refused by name. `--fix` re-derives the manifest; `tools/parity_suggest.js` says which op would have matched. The shared core is derived, not declared: an op that reimplements what the page does shares no symbol with it and is caught. `gapBudget` may only shrink. Full text: `docs/CONVENTIONS.md` → "The parity gate".
6. **Zero-Trap & Self-Healing Gateway (`af.js`):** If you discover any escaping, encoding, redirection, timeout, or CLI usability defect in `af.js` (`src/service/af.ts`), **fix it in the code immediately on the spot rather than documenting it as a caveat or trap.** Every build must leave the bridge gateway more robust for the next agent.
7. **SESSION LAUNCH PARITY & ENTRY POINTS DISCIPLINE:** When a session parameter, option, or dimension (e.g. `superpowers`, `projectId`, `engine`, `model`, `effort`, `permissionMode`, `name`, `prompt`, `attachments`) is introduced, modified, or extended, it MUST be supported, wired, and tested across **ALL 11 session launch entry points** in the same commit. Adding an option to the Console composer alone and forgetting the launcher, profiles, or tree menus is a structural failure.
   - **‼️ The last-used setup is a LAYER, not a per-door feature (S-34).** A door that starts a session seeds with `seedLastLaunch(agentId, o)` and records with `rememberLaunch(agentId, o, surface)` — both in `src/extension.ts`, both thin wrappers over `withLastLaunch` / `launchToRemember` in `src/core/launch.ts`. Never read or write `agentfarm.lastLaunch` directly, and never inherit the record by hand: a new dimension on `LaunchOptions` is then remembered by the shape rather than by ten call sites. The bridge is the one deliberate asymmetry — `sessions.start` RECORDS and does not inherit.
   - **‼️ A REOPEN asks what the session CLOSED with (S-109).** A door that opens a session again (any Resume, Continue, a task continuing its conversation, a baton leg) takes model/effort/permission/account from `reopenFor` (`src/launch/reopen.ts`) and is listed in `src/launch/reopenDoors.ts` in the same commit; `test/test_reopen_parity.js` fails an unlisted resuming spawn and a door that orders the layers itself. A baton leg's account stays S-106's. Full text: `docs/CONVENTIONS.md` → "A REOPEN asks one answer".
   - **The 11 Entry Points:**
     1. **Console Composer (Pre-spawn):** `ConsolePanel` / `media/console.js` (empty state / `+ New Session` / pinned agent composer).
     2. **Sidebar Agents Tree Inline (`▶`):** `AgentsTreeProvider` -> `agentfarm.startSession`.
     3. **Sidebar Agents Tree Context Menu:** `agentfarm.startSession`, `agentfarm.launchSession` (`runLauncher`), `agentfarm.startSessionWith`, `agentfarm.consoleForAgent`.
     4. **Launch Profiles:** `agentFarm.launchProfiles` / `src/core/launchProfiles.ts` (saved setups).
     5. **Multi-Dimension Launcher:** `runLauncher` (`LaunchOptions`, QuickPick rows).
     6. **Surface Selector:** `pickRunSurface` (Terminal vs Console).
     7. **Projects Tree & Page:** `ProjectsTreeProvider` & `projectsPage.js` ("Start session under project").
     8. **Webviews / Pages:** `agentDetail.js` ("Talk to Agent", "Launch Session"), `dashboard.js`, `missionsPanel.ts`, `portfolioPanel.ts`.
     9. **Command Palette & Status Bar:** `agentfarm.startSession`, `agentfarm.launchSession`, `agentfarm.openConsole`, `agentfarm.continueSession`.

It has no pickers: every dimension comes from `seedLastLaunch` + the agent's defaults, so a new dimension reaches it through the layer — but it must still be carried by `startConsoleSession`.

**‼️ A NEW SETTING GETS A CATALOG RECORD:** when contributing an `agentFarm.*` setting in `package.json`, add its record to `src/core/settingsCatalog/<section>.ts` in the same commit — its group, its tier, and once written its name and one-line summary. Everything a person reads about a setting lives there and nowhere else. Without the record `test/test_settings_catalog.js` fails, naming the key. Full text: `docs/CONVENTIONS.md` → "Adding a setting".

**‼️ A NEW USER PREFERENCE IS A FLEX POINT (X-367):** any box, setting or bridge argument a user chooses a value in gets its point in `media/afFlex.js` in the same commit — each level with its surface AND bridge key; values are resolved and explained by `resolveFlex` (`src/core/flexResolve.ts`), never by a surface's own fallback chain. Full text: `docs/CONVENTIONS.md` → "A preference is a FLEX POINT".

**‼️ NEW INTERFACE TEXT GOES THROUGH `t()` (U-189), on every page, wired or not** — a table phrase translated where it is drawn is marked `N_('…')`; `test/test_i18n_ratchet.js` fails a page whose bare English grows. Full text: `docs/CONVENTIONS.md` → "The interface language".

**‼️ A TEST THAT CALLS `activate()` RUNS AGAINST THE REAL MACHINE (X-265).** `cfgValueRaw` asks the vscode registry first and falls back to **reading the user's own `settings.json` off the disk** when it answers `undefined` — which every stand-in does. So `test_activation.js` ran with this machine's real `agentFarm.*` values and a real `os.homedir()`, and a suite run rewrote `~/.claude/settings.json` and seeded three account directories. Before adding **any** `fs` write to activation, check the sandbox in that file still holds (`USERPROFILE`/`HOME`/`APPDATA`/`LOCALAPPDATA`/`XDG_CONFIG_HOME` → a temp dir, asserted at the end). And a fixture belongs in `os.tmpdir()` with an `af-` prefix, never inside `test/`: a test that THROWS never reaches its cleanup, and the leftover walks into the next `git add -A`.

**UI — `docs/CONVENTIONS.md` in the repo is binding;** read it before touching `media/` or `src/panels/`. The visual gate and the five names are universal (`_REF/ui-conventions.md`); this repo's instruments:

- **Measure:** `node test/measure_page.js <fixture> "<expr>"` runs against the laid-out DOM; a repaired layout defect gets a measuring guard.
- **AFTip** is `media/afTip.js`; it yields to the hand itself (a press or key mutes it until the pointer leaves). Two hover surfaces only: AFTip for anything that is or could grow into text, a native `title` for a handful of figures. **Before `npm run package`, run `git status`** (`_REF/engineering.md` → parallel sessions): another session's uncommitted files compile straight into your VSIX. A shared file's single hunk is committed with `git update-index --cacheinfo`; a mixed VSIX is neither committed nor installed.

**Delivery:** Package with `npm run package` — **never a bare `vsce package`**, which drops the VSIX in the repo root. Every build belongs in `dist/vsix/`, which is where the script's `--out` sends it and where the whole history of builds already lives. Packaging is not enough — **install** it with `code --install-extension dist/vsix/agent-farm-<v>.vsix --force`; **then load it yourself — an installed VSIX is not the running code:**
- **Mid-session verification reload (continuing work in this session):** `node $b farm.restartExtensionHost resume=true`, then poll `node $b farm.health` until `bootId` changes and `build.pending` is `false`. (See below on S-59 / X-266 for the revive contract).
- **End-of-session handover reload (wrapping up work):** ‼️ **NEVER use `resume=true`!** If your work is done and you are handing over, present your final response to the user in chat first, then as the final tool call invoke `node $b farm.restartExtensionHost resume=false` (or bare restart). The host reloads, the build is live for the next agent, and this session terminates cleanly without a wasteful context re-read or a forced goodbye turn. **Not in a baton relay:** there the successor loads the build first (`_REF/handover.md` → Baton relay).
‼️ A HOST RESTART ALONE NEVER LOADS A NEW BUILD (measured in VS Code 1.103.2): `workbench.action.restartExtensionHost` restarts the hosts from the extension registry the window already holds and never re-scans the extensions folder, so the OLD version comes straight back — which is why the Extensions card keeps its "Restart Extensions" button, reading the difference live. Only a window reload re-scans, so the op now plans one for you when `build.pending` (`build.escalatedFrom` + `note` say so; `loadBuild=false` opts out). That means open terminals block it: an unattended build-load belongs in a Console session rather than a terminal. Then confirm the install actually took: VS Code marks a version obsolete on rollback and keeps serving the previous folder, so read `version` for `muvusoft.agent-farm` in `%USERPROFILE%\.vscode\extensions\extensions.json` — the folder existing proves nothing.
- **‼️ AND IF YOU CALLED A MID-SESSION RESTART (resume=true) FROM INSIDE THE SESSION IT REVIVES, YOU WILL BE KILLED AND RESUMED — COMMIT AND WRITE YOUR PROJECT RECORDS BEFORE IT, NEVER AFTER (S-59 / X-266).** The window reload kills the extension host but NOT the session's own `claude -p`; the revive on the new host RECLAIMS the row first (`ConsoleHost.reclaim`: the registry holder is ended, its record watched until it drops, only then `--resume <sid>` is started once — the card's first line names the pid it ended). The reply you were writing is lost; the resumed copy gets the revive nudge, so **your last text before the restart is the instruction it will follow** — write the verification steps there. This holds on the `armed` path too (the nudge follows your CONSENT, not whether your turn was cut), and the op's answer tells you before you commit to it: **`reviveIntent` names your seat and says whether it will be spoken into** — `nudge:false` means your last words are simply lost, so read it rather than assuming. Verify from the other side with the CLI's own registry, never a process list (`Get-CimInstance` ran seconds before a copy was born and reported CLEAN): `<config-dir>/sessions/<pid>.json` holds `{pid, sessionId}` per live process, **two files naming one `sessionId` IS the twin**, and `farm.health` → `sessions.twins` reads exactly that across every claude home (‼️ the registry is per home — a slot session's record is under the slot, and `~/.claude/sessions/` stays empty). If the revive reports the row as LOST ("still holding this session, pid N"), the survivor could not be ended: it keeps working with its words on a dead pipe — a session in that state does durable work only (records, commits, Notices) and does NOT keep changing a live product nobody can steer. A Console-hosted TASK row follows its conversation into the revived card by the engine session id (S-88); without that id it stays parked. An ordinary reload without `resume` revives nothing, and its survivors are listed by `farm.health` → `sessions.leftovers` (S-59: program-owned, on no seat here or elsewhere; `ours` = console | task). The task gate and `console.start resume=` end a leftover that is OURS and refuse any other holder by name; one with no `ours` is somebody else's SDK — report it, never kill it. ‼️ AND KNOW WHICH KIND OF SESSION YOU ARE BEFORE YOU RESTART: a project session spawned as a one-shot `claude -p` by a task (grand-parent pid = the extension host, no seat in `console.sessions`) has NO revive — a reload orphans it. Such a session installs the build, leaves `build.pending`, and hands the load + the live check to the next Console session.

**‼️ AND VERIFY WHAT IS ACTUALLY INSIDE THE BUILD: `npm run verify` (`tools/verify_vsix.js`).** Every other gate runs BEFORE `vsce`, so `.vscodeignore` — a list of patterns — can drop a new `media/*.js` or `out/panels/*.js` silently: the extension installs cleanly and the page is blank the first time it is opened. This reads the artefact's own zip listing and checks that every panel, core module, media asset and shell-requested script is really in it (and that `src/`, `test/` and the manifest are not).

**Encoding:** `package.json` carries every menu title, tooltip and settings description, and has twice been damaged by a CP1252 round trip. The pre-commit hook and `npm run package` both run `test/test_encoding.js`; repair with `--fix`. Shell payloads: `_REF/shell.md`.
