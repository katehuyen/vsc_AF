# Git / Commit Discipline

The user has their own commit system; follow it **exactly** — never commit on your own judgment. **Read this BEFORE committing.** Two repo types, two formats:

## A. Work/product repos (every product or work repo)

**Scope:** every repo that already uses the `v#.#` counter (e.g. `vsc_AgentFarm`, `and_AgentFarm`) and **every new repo** — its counter starts at its first formatted commit (`_REF/project-bootstrap.md`). An existing repo with its own history is not migrated; it keeps its format unless the user moves it.

1. **When:** Committing when the work is done is the **default behavior** — do not wait for the user to say "commit it"; commit once the work (code+tests+package+docs) is complete. Skip only if the user says "don't commit / hold off".
2. **ONE commit, everything included:** One job = one commit. The produced package (e.g. a VSIX) is **inside that same commit**; after committing, no new or untracked files remain. Only your own paths: parallel sessions share the working tree (`_REF/engineering.md`).
3. **Message format:** Title `v#.# - <version>: <lowercase summary>` for a release, `v#.# - <lowercase summary> (not released)` otherwise. `#.#` is the **global commit counter** (not a version number): the last `v#.#` in `git log` + 1 (unformatted intermediate commits also consume a number). Blank line + **body:** the **final summary answer** given to the user that turn, file by file. **Verification proof mandatory:** the body states the outcome (`Full suite N files / M passed / 0 failed`, the CI run that proves the rest, specific manual verification steps, or `Pure documentation edit (exempt)`). A `Limit:` line names anything the change does not cover or could not verify.
4. **Version and CHANGELOG:** the release version lives in **one** place (package manifest, a build-file constant) and ≠ the commit counter — they increment separately. A release bumps it and adds `## <version> - <title> (<YYYY-MM-DD>)` to `CHANGELOG.md`, user-facing and in the user's language; release notes shown to users are read from that entry, and a gate test holds the version and the newest entry together.

## B. Agent repo (git root `D:\zone\agent` — agents plus `_run_folder_move` claude/vscode state; the agents' own backup)

1. **Message format:** `vYY.M.D.N - <short description>` — YY=year, M=month, D=day (no leading zero), N=**which commit of that day** (check git log for the last number, +1). Example: `v26.7.18.4 - basit agent added`. The description briefly states what changed; never left blank.
2. **Daily backup:** Every day at **05:00** the `basit` agent commits the repo in this format (if missed, it runs at the first opportunity without asking). If there are no changes, no commit is made. After the commit it runs `_setup\Push-Backup.ps1` (X-337): GitHub and the local vault, each tried on its own, one line per home.
3. **Important optimization = immediate backup:** Whichever agent it is, when it makes an **important optimization or rule change** to the agent system (constitution, `_REF/`, an agent's `CLAUDE.md`, memory structure, `DUTIES`, a new agent…) it commits in the same format **immediately, without waiting for the daily backup and without asking**.
4. ‼️ **This repo is a MIRROR of machine state — stage the WHOLE repo, never a path list.** Always `git add -A`. A hand-picked add leaves machine state behind silently, and the commit body will still claim it shipped: measured 2026-09-12, a commit whose body read "five account slots patched" carried two files, the five patched files stayed in the working tree, and a fresh clone would not have had the key at all. The body is not evidence — `git show --name-only` is. The ignore list already encodes the intent (**everything in, only certain noise out**), so there is no third state: after the commit `git ls-files --others --exclude-standard` must answer **empty**, and whatever is left is either noise → a `.gitignore` line, or information → belongs in this commit. `git add -A` on this repo can take minutes and can lose a race with VS Code's git refresh over `index.lock`; retry in a loop, never delete the lock.

## ‼️ `git checkout -- <file>` is not an undo — it is a restore to HEAD

A mutation test edits a file on purpose and then has to put it back. `git checkout --` does not remove your mutation; it replaces the file with **HEAD**, taking every uncommitted line in it along. Measured: 125 lines of finished, tested work were deleted by one such command and had to be rebuilt from a stray `/tmp` copy plus the previous session's transcript.

1. **Commit before you mutate.** A mutation is proof that a guard bites, not part of the change — the change belongs in git before the proof is attempted.
2. Mutating uncommitted work anyway means restoring from a **copy you made yourself** (`cp f f.bak` … `cp f.bak f`), never from git.

## ‼️ The global-ignore trap — `git status` is not proof

A clean `git status` does **not** mean everything is in git. Three mechanisms hide files without any entry in the repo's `.gitignore`:

1. **Machine-local global ignore** — `~/.config/git/ignore` (git reads this path by default; `git config --get core.excludesfile` returns **nothing**, so it looks like there is no global ignore). Claude Code writes `**/.claude/settings.local.json` into it. It does not travel with the repo → another machine hides a different set of files.
2. **Empty directories** — git cannot track them at all. A folder that must exist (a symlink target, an output dir) vanishes on clone. Fix: a `.gitkeep` inside it.
3. **Nested `.git` folders** — git does NOT simply skip them: `git add -A` records the folder as a **gitlink** (mode 160000) pointing at a commit this repo does not have, and the subtree's files are never staged. Measured 2026-09-13 on the agent repo: the plugin marketplace reached three slot junction paths and `add -A` wrote three dead submodule pointers; a fresh clone errors on them. The warning it prints (`adding embedded git repository:`) scrolls past in a 500-file add, so **read `git ls-files -s | grep ^160000` after a backup**, not the console (`Doctor.ps1` → `backup / junction shadows` does). And where the subtree's files WERE tracked before the `.git` appeared (the pool's plugin marketplace), git keeps those paths but adds no new file under it and reports **0 untracked** — compare `find -type f` against `git ls-files` there before trusting the count.

**Audit command** (run before trusting a backup, and after adding an agent):

```
git ls-files --others --exclude-standard        # untracked, honouring every ignore layer
git check-ignore -v <path>                      # names the file:line that hides it
find <dir> -type d -empty                       # dirs git will drop
```

When a **critical** file turns out to be hidden by a layer outside the repo, do not fix it with `git add -f` — that only fixes this one file on this one machine. Put a **negation rule in the repo's `.gitignore`** (`!**/…`); a repo `.gitignore` outranks the global ignore, so the repo defends itself everywhere (portability rule, constitution).

## ‼️ The 'git status --short' leading whitespace trap — use trimEnd(), never trim()

In `git status --short` output, the first 2 columns represent file status (column 1 = index/staged, column 2 = working tree).
Trimming leading whitespace with `trim()` mutates `" M file.ts"` (unstaged) into `"M file.ts"` (staged), causing parsers and pre-commit checks to silently misidentify staging state. Always use `line.trimEnd()` or slice by index (`line.slice(0, 2)`).
